# 支持范围与验证矩阵

本矩阵描述当前 `0.1.0-preview.1` 的交付入口、证据范围和待验收项。它不把“代码接受配置”“安装包可生成”或一次局部测试解释为整机兼容。组件来源和字节锁来自 [components.json](../integrations/metacubexd/components.json)，审核记录见 [review.json](../integrations/metacubexd/review.json)，产品验收结论与限制见[发行说明](release-notes.md)。部署前同时核对[设备条件](cooperating-router-requirements.md)和[路由器契约 v1](router-contract.md)。

## 支持状态与证据等级

支持状态回答“该组合在声明的范围内是否适用”，证据等级回答“依据是什么”。两列独立填写；构建通过不会自动提高支持状态，某个场景达到 E3 也不表示完整维护已经通过。

| 支持状态 | 判定范围 |
| --- | --- |
| 已验证 | 指定版本组合完成了该条目列出的验收；结论仅覆盖这些场景 |
| 有条件支持 | 需要明确组件、设置或限定场景，并已有相应运行证据；条件及未验项目必须同时列出 |
| 待验证 | 当前入口或条件可能适用，但缺少相应目标运行或完整组合证据；不能仅凭工具名称、配置格式或契约字符串宣布支持 |
| 不满足当前要求 | 缺少当前模式必需的能力，或超出当前安装/拓扑入口；须补齐能力或另行实现后重新验收 |

| 等级 | 必须具有的证据 | 不能由此推导的结论 |
| --- | --- | --- |
| E0：实现范围 | 源码、配置校验及文档定义了入口和限制 | 能在某台设备运行 |
| E1：构建与合成检查 | 固定输入、类型或合成测试、装配及字节校验通过，并记录对应提交 | 目标 OS、内核、systemd 或路由器可用 |
| E2：隔离运行 | 真实组件在注明边界的回环、网络命名空间或实验环境运行 | 实体接线、物理重启、固件生命周期及持续负载通过 |
| E3：物理组合验收 | 指定版本的主机、OS/内核、路由器固件及终端完成逐项验收 | 其他组合或未执行场景通过 |

证据按场景逐项记录，不能给整个平台笼统升级。E3 中尚未执行的场景仍是待验收。目标只读预检通过证明当次可观察的前置条件；完整路径、故障阻断和独立关闭仍须运行验收。

## 外接设备与组件

| 对象 | 当前入口 | 当前证据与限制 |
| --- | --- | --- |
| Linux ARM64 | `linux-arm64`，固定 Mihomo v1.19.33；Linux/systemd 安装入口 | E1 构建/装配、E2 真实核心隔离运行；发行说明记录 E3 的安装、升级、管理和部分代理路径。整机断电、物理换口、实体多终端和长期负载仍待组合验收 |
| Linux x86-64 | `linux-amd64-v1`，固定 Mihomo v1.19.33；同一安装器核对目标架构 | E1 固定资产及装配入口。`review.json` 的该平台 `runtimeVerified:false`，尚无目标运行验收结论 |
| Linux 发行版/内核版本 | 按 Node.js、systemd、polkit、TUN、iproute2、nftables 和权限能力核验 | 当前没有逐发行版/内核版本的认证名单；满足软件名称或版本号不能替代 JSON 命令能力、系统策略及生命周期验收 |
| 无 systemd、其他架构、Windows/macOS | 不在当前目标安装入口范围 | 在这些系统开发或运行合成测试不构成目标服务部署支持 |
| 普通端口映射容器 | 不在当前原生网关安装入口范围 | 端口可达不能提供主机 TUN、策略路由、早期 guard 与独立 unit 的完整行为 |
| MetaCubeXD 管理端 | 固定 v1.273.1 提交与 overlay，单实例 Node Server | E1 UI/Server 构建及适配 UI 类型检查；E2 回环管理/浏览器流程。`review.json` 不宣称上游全量类型检查或完整 systemd 集成通过 |
| Mihomo 核心 | 固定 v1.19.33，各架构独立摘要 | ARM64 的 E2 范围含语法、显式代理、回环 DNS、Controller HTTP/流量流；它们不证明透明接管或路由器回程 |
| HTTPS 与通知 | 匹配 origin/Host 的证书和反代；通知还受浏览器、证书信任及权限约束 | 按[HTTPS 配方](management-https.md)和[通知条件](notifications.md)单独验收，HTTP 回环证据不覆盖远程 HTTPS |

Node.js 最低版本为 22.18；原生网关还需 Python ≥3.9 及安装文档列出的固定命令路径。当前没有经过跨设备测量的通用最低 RAM、磁盘容量或吞吐承诺；应以解包/双 release/私有状态所需空间及目标并发、CPU、内存和链路测量确定余量。

| 待验证 | 明确固件/组件/适配器版本映射，完整 R1–R9、DNS/链路等故障、正常重载、冷启动顺序、物理换口、多台实体终端及持续负载 |

## 路由器、流量与拓扑

| 场景 | 当前范围 | 验证状态与动作 |
| --- | --- | --- |
| 路由器固件 | 满足[契约 v1](router-contract.md)的行为实现；不依赖统一厂商命令 | 有一个可选适配器组合的部分实机证据；没有全品牌、全原厂固件或全 OpenWrt 版本支持结论。逐固件/组件版本映射并验收 |
| 同子网 LAN IPv4 | `clientCIDR` 精确等于外设接口子网，排除路由器、外设和网络/广播源地址；支持普通客户端动态加入 | E0 范围；E2 真实核心多来源覆盖双客户端 TCP/UDP、新地址、经路由器回程、DNS 和核心停止阻断。实体多终端并发仍待 E3 |
| 单终端兼容输入 | `clientIPv4` 与 `clientCIDR` 互斥 | 原范围保持；转为 LAN 范围前显式关闭并协调两端配置，不把旧输入自动扩大 |
| DNS | 路由器按 UDP/TCP 转交受管公网查询；本地域名保持基础解析；bootstrap 独立 | 局部 DNS 预检只证明查询可达，不能替代客户端出口/回程证据 |
| IPv6 | 受管公网 IPv6 阻断，必要本地控制与管理由路由器保留 | 没有完整 IPv6 代理交付；必须验证不存在未受控公网旁路 |
| 加密 DNS、其他 IP 协议 | 由路由器声明处理范围并单独验证 | 不从 TCP/UDP 转发成功推导任意应用 DNS 或其他协议行为 |
| 单网口、同一逻辑 LAN 重连 | 设计允许交付、出站和回程共用接口；恢复依据上次成功配置及新鲜证据 | 物理换口/拔插、启动次序及目标固件重载仍须 E3；60 秒为依赖就绪后的验收目标 |
| 跨网段、终端直接用外设作 DHCP 网关、桥接或 VPN 入口 | 尚未交付这些拓扑的完整适配 | 不能仅改地址或放宽来源字段进入当前支持范围 |
| 任意防火墙停止/全表 flush | 无连续阻断保证 | 与正常受支持的 reload 分开记录，不能宣称零窗口 |

当前原生网关由 [gateway](../packages/gateway/README.md) 与部署入口实现。[network 保留框架](../packages/network/README.md)的独立约束和证据不能直接套用于当前原生部署。

## 增加一项兼容结论

1. 按上述字段新建组合记录，记录日期、CoCoProxy 提交/载荷 manifest 摘要、核心资产及指令集条件、管理 overlay、OS/内核/systemd/运行时/工具版本和实际能力、安装方式、路由器固件/组件/适配器版本及必要配置；硬件只保留必要脱敏范围。无法追溯的事实写未记录，未执行场景写待验证。
2. 分别执行安装前置检查、管理 HTTPS、DNS、TCP/UDP、DIRECT/代理目标、原始来源、出口及经路由器回程验证。
3. 按契约验证故障阻断、外设离线后独立关闭、正常重载、重启次序、断线恢复，以及范围变更后的新加入终端；记录每项执行/未执行状态。
4. 分开填写支持状态、各项 E0–E3 证据、四里程碑、首装/升级/卸载/重启恢复及规模测量。先补完整现有组合，再新增外设系统，随后扩展固件组合；每个新结论都附对应入口与限制。
5. 把原始环境和恢复记录留在被忽略的本地资料。正式文档只提交可复用步骤、对应版本、脱敏结论和剩余缺口。

`review.json` 当前的 `compatibilityVerified:false` 保留其原意；不能为了发布或通过检查将它改成 `true`。新增证据需注明具体范围，存在缺口时继续限制支持结论。
