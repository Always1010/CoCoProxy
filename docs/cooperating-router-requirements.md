# 协同路由器要求与说明

## 产品与角色

Coproxy 是独立部署在外接 Linux 设备上的代理产品，承担代理协议、加密、分流、DNS 和运行配置管理，提供浏览器入口管理订阅、节点及代理参数。协同路由器负责终端接入、基础路由、流量转交和独立关闭。两者按网络能力协作，不要求来自同一个项目，也不要求路由器采用某种固件或管理界面。

AlwayRoute 是可选的路由器侧实现，用于复用已经开发的流量转交、开关、DNS 协调和恢复能力。Coproxy 不以安装 AlwayRoute、访问其 RPC、使用其账户或先刷 OpenWrt 为启动条件。符合下文全部条件的原厂固件可以保留；其他组件也可承担同样职责。

“独立部署”指 Coproxy 有自己的软件包、配置、账户、状态、服务和管理入口。实现终端透明代理仍需网络中的路由器把流量按约定交付，不能把设备安装成功等同于整个局域网已接管。当前实现是一种明确的交付方式，不覆盖所有旁路网关、VPN、桥接或全网拓扑。

接入路由器同时承担两种角色：先在 LAN 侧把终端原始访问交给 Coproxy，再在 WAN 侧把 Coproxy 的代理出站送往外部节点。它们是不同连接／会话，响应也要先回核心处理，再经路由器送回终端。完整分步图见[终端访问公网的数据流](traffic-flow.md)；管理浏览器访问 Coproxy 的网页是另一条管理路径，不与业务转发混画。

## Coproxy 外接设备自身的条件

完整安装、维护和卸载方法见[可重复部署](deployment.md)，网页与证书见[HTTPS 网页部署](management-https.md)。以下是当前安装器和原生自动网关的实际约束，不是所有未来发行形态的永久限制。

| 项目 | 当前条件 |
| --- | --- |
| 系统与架构 | Linux/systemd；已审阅的 ARM64 或 x86-64 ELF64 little-endian 核心，核心、操作系统与 Node 架构匹配。ARM64 有实机安装及终端证据；x86-64 已有固定载荷校验，仍需目标运行验收。其他架构、Windows、macOS、无 systemd 系统及普通端口映射容器不在当前安装入口支持范围 |
| 运行软件 | Node.js ≥22.18，现有 systemd、支持 JavaScript rules 的 polkit；自动网关另需 Python ≥3.9、可用的 iproute2/nftables。网页配方使用既有 nginx 和匹配证书，生成本地证书时需要 OpenSSL。系统工具及账户由操作者准备，安装器不自动装依赖 |
| 内核与权限 | `/dev/net/tun`、TUN、nftables、策略路由及所用 JSON/规则能力可用；安装由 root 执行，管理与核心使用专用非登录 UID。管理服务不获网络 capability；核心与独立网络单元按部署计划取得所需权限 |
| 转发与系统策略 | 操作者显式准备 IPv4 转发，核对防火墙、rp_filter、重定向、SELinux/AppArmor、服务 sandbox 和既有网络资源；安装器不自动修改系统 DNS、默认路由或 sysctl。Linux 的 `ip_forward` 变更可能重置其他 IPv4 参数，不能只改一项而忽略现有系统配置 |
| 网络接口 | 至少一个符合当前模式的非 loopback、非 TUN IPv4 接口；可使用满足条件的物理或虚拟接口，不要求某种接口名称或必须双网口。指定接口必须 UP，配置稳定地址，能在同一 IPv4 子网直接到达协同路由器和受管终端 |
| 地址与范围 | 当前配置只接受一个受管终端 IPv4；路由器、外设、终端地址不同，均为同一前缀中的有效主机地址，前缀范围为 /1–/29，不能覆盖保留 TUN 网段。实际选型不应因此使用过大的 LAN。多终端、跨三层网段、桥接及双栈接管尚未交付 |
| 资源容量 | 磁盘要容纳清单中的解包载荷、当前与新版本、暂存及私有状态；不能只按压缩包大小估算。CPU、RAM 与链路余量需按并发、协议及目标带宽测量；目前没有最低 RAM/CPU 或全设备吞吐基准，不承诺任意硬件可运行或达到某个带宽 |
| 管理与维护 | 局域网浏览器可达独立 HTTPS 入口，凭据和私钥私有保存；具备不依赖代理的维护通道。先完成安装、配置应用与验收，再明确配置持久转发和服务开机启动 |

Linux 转发开关的副作用依据[内核 IP sysctl 文档](https://docs.kernel.org/networking/ip-sysctl.html)。具体能否运行仍由目标上的预检、启动和终端验收决定。

## 当前交付方式要求路由器具备什么能力

终端默认网关及基础 DNS 入口保持为协同路由器。路由器把选定终端的受管公网 IPv4 TCP/UDP 交给 Coproxy，**保留终端源 IP，由路由器的交付接口 MAC 发出**；Coproxy 的新建出站及终端回程均经该路由器。当前 root guard 和 `/32` 回程依赖这条路径，不是 AlwayRoute 专有协议。

| 能力 | 配置要求及验收点 |
| --- | --- |
| 终端接入与稳定身份 | 原有 LAN、DHCP、基础 DNS 和 WAN 正常。通过地址保留或明确静态配置固定外设及受管终端身份，核对接口 MAC；随机 MAC 或地址变化后须重新核对范围 |
| 受管来源选择 | 能按终端来源及必要的入接口选择流量，仅把受管公网 TCP/UDP 交付外设。局域网、路由器、外设管理与基础控制流量保留，不扩大到所有终端 |
| 下一跳及防循环 | 受管公网下一跳是外设；路由器自身、外设新建连接和回程不再次交付外设，外设仍经路由器的正常 WAN 出站。不能把路由器全局默认路由盲目改成外设 |
| 来源与链路身份 | 路由器到外设的交付保留终端 IPv4，不能在这段做 SNAT/masquerade；帧源 MAC 与配置的路由器交付 MAC 一致。原有 WAN NAT 可继续存在。不能用地址转换掩盖回程或身份问题 |
| 回程和连接跟踪 | 接受外设经路由器返回终端的响应，允许实际部署所需的同接口转发；核对防火墙状态、反向路径校验、ICMP 重定向及 MTU。当前 Coproxy 把受管终端 `/32` 回程显式交回路由器 |
| 受管 DNS | 只把受管终端的公网 DNS 交给外设指定端口，覆盖 UDP/TCP。本地域和无点名称保留基础解析，bootstrap 不循环依赖代理 DNS。当前外设 DNS 只接受配置的路由器地址/MAC及本机请求，不能让终端直接查询外设来绕过该边界 |
| IPv6 与其他协议 | 当前受管公网 IPv6 必须由路由器阻断，保留必要的本地 IPv6 控制和管理；不能因 IPv4 已转交而放任 IPv6 从 WAN 绕行。其他协议及 MTU/必要 ICMP 差错须明确处理，不宣称支持任意 IP 协议 |
| 故障阻断 | 外设、核心、DNS 或链路故障时阻断受管外网，保留开启意图，不自动退回 WAN 直连。策略路由查表失败或移除下一跳后不能继续落到普通 WAN；固件的自动 failover 也须符合此策略 |
| 独立关闭 | 外设关机或失联时，路由器仍可从自己的管理入口撤销交付、专用 DNS 和相应 IPv6 限制，恢复普通直连。不能要求先登录 Coproxy 才能关掉路由器接管 |
| 加速与生命周期 | 受管范围不能被软/硬件 offload、桥接加速或既有连接绕过。保存、应用、撤销及部分失败可核对；重启、接口重连和防火墙/DNS重载后保持意图与故障边界，先保护再放行 |

策略路由可依据来源、入接口等字段选择下一跳，普通目的地址静态路由不能直接替代这些能力，见[ip-rule 官方手册](https://man7.org/linux/man-pages/man8/ip-rule.8.html)。SNAT 会改变来源，普通端口映射也不是完整 IP 流量交付，见[nftables NAT 文档](https://wiki.nftables.org/wiki-nftables/index.php/Performing_Network_Address_Translation_(NAT))。这些资料解释机制，不替任何固件作兼容保证。

路由器不必使用 nftables、Linux 命令或 AlwayRoute 字段；其他网络栈、厂商配置界面或插件只要实现同样行为即可。Coproxy 外设上的当前 Linux 实现则使用上述系统工具。

## 原厂固件、安装组件或更换固件如何判断

| 路由器现状 | 结论与下一步 |
| --- | --- |
| 原厂固件已提供上述完整能力，配置可持久保存并可独立关闭 | 可以保留原厂固件及原管理方式；按能力映射配置并完成当前组合的验收，无须为 Coproxy 刷 OpenWrt 或安装 AlwayRoute |
| 原厂系统允许受支持的插件/脚本，所缺功能可由组件补齐 | 优先补齐经过审阅的组件；确认接口、权限、开机及重载行为、升级兼容和撤销方式。可选 AlwayRoute，也可选其他满足要求的实现，不因能执行脚本就视为全部支持 |
| 只有普通静态路由、修改 LAN DNS/DHCP 或端口映射 | 信息不足，不能认定符合当前交付方式；逐项检查来源选择、排除、防循环、DNS端口与来源、IPv6、故障及独立关闭，不直接指导刷机，也不假称“改个网关就行” |
| 固件缺少关键能力且无法安装合适组件 | 当前模式不能直接使用；可以选择具备能力的另一台协同路由器，或在确认精确硬件支持及恢复条件后更换固件。OpenWrt 是一种选择，是否能刷取决于硬件、容量和维护支持 |
| 接口/加速/IPv6行为不明，无法核验 | 标记“待核验”，补充厂商文档、只读检查或限定终端测试，不把未知记为支持 |

“支持 VPN 客户端”“支持策略路由”“支持自定义 DNS”是线索，各功能的具体行为仍需核对。例如某个策略路由菜单可能只支持路由器内置 VPN，并不能把原始流量交给另一台 LAN 主机；某个 DNS 输入框只能填 IP 的 53 端口，也不支持当前所需的选择性转交。

以下方式**不是当前已支持的替代部署**：

- 只通过 DHCP 把终端默认网关改成 Coproxy：终端会用自身 MAC 直接发给外设，与当前路由器交付 MAC 校验不符，终端默认网关和关闭语义也发生变化。
- 只把路由器全局默认出口改成 Coproxy：没有外设和本机流量排除会形成循环，也没有解决 DNS、故障及回程。
- 只把终端 DNS 或 DHCP DNS 改成 Coproxy：当前 DNS 不监听通用的终端 53 入口，且限制查询来源；DNS 变更本身也不能代理 TCP/UDP。
- 端口转发、HTTP/SOCKS 客户端代理、VPN 隧道或桥接串联：各有不同入口与身份语义，不能套用当前透明交付配置。若未来提供这些模式，需要明确配置和独立验收。

## 不使用 AlwayRoute 的配置与落地流程

操作者使用路由器原有管理界面、受支持的命令入口或其他组件完成配置。Coproxy 不主动写路由器，也不要求双方建立控制连接。配置前用一份经核验的角色记录对齐下表；合成样本见[自动网关输入](../examples/automatic-gateway-deployment.json)，不能原样使用。

| Coproxy 输入 | 路由器配置或现场对应值 |
| --- | --- |
| `automaticGateway.gatewayIPv4` | 外设稳定 IPv4；受管流量交付的下一跳 |
| `automaticGateway.routerIPv4` | 协同路由器在交付链路上的 IPv4；外设标记出站和回程下一跳 |
| `automaticGateway.routerMAC` | 路由器交付接口的实际单播 MAC，不填外设或终端 MAC |
| `automaticGateway.clientIPv4` | 唯一受管终端 IPv4；路由器按实际终端 IP/MAC 限定范围 |
| `automaticGateway.ingressInterface` | 外设侧接口名称；路由器另配置自己的接口，两台设备的名称不必相同 |
| `automaticGateway.prefixLength` | 当前三个角色共同所在子网前缀 |
| `automaticGateway.dnsPort`、`management.deployment.dnsPort` | 必须相同；路由器把受管公网 DNS 转交到外设此端口，例如合成端口 `15353` |
| `management.deployment.bootstrapResolvers` | 外设可独立使用的解析入口，不能循环指向受管 DNS 链 |
| `management.origin` 与网页配置 | 局域网可达的 HTTPS 地址、证书及 Host 一致；用域名时基础 LAN DNS 能解析 |
| `egressMark`、`egressTable`、`egressPriority` | 外设自己的网络资源预留；路由器使用自己的资源，不要求同号 |

建议按以下顺序落地：

1. 保留现有固件，先核对能力表及维护入口。每一项记为“满足／待核验／缺少”，缺少关键项时先选择组件或替代路由器，不先修改默认出口。
2. 独立安装 Coproxy，配置账户、HTTPS、可信部署参数及订阅/节点，应用候选并确认核心和 DNS。此阶段不要求路由器安装任何 Coproxy 配套包。
3. 在路由器准备一个明确终端的流量选择、例外、来源保留、DNS、IPv6阻断及故障规则，先验证独立关闭路径。DNS 转交和公网交付应协调应用，失败时不能留下半套路径。
4. 开启交付，用真实终端验证代理目标与规则直连目标、DNS、本地管理、来源、出口和回程；确认外设自身不会被送回自身。
5. 分别验证核心/DNS/链路故障时受管外网阻断，以及外设离线时从路由器关闭后普通直连恢复。不能只测 ping、服务 active 或打开一个已有缓存页面。
6. 核对持久意图、重新应用方式、服务与网络重载，并在获准窗口完成重启及持续运行验收；记录固件/组件版本、参数映射和已验证范围。

不同原厂系统的菜单和命令不同，本文规定必要行为及参数，不提供一条可在任意路由器执行的修改脚本。没有某个固件的文档或设备证据时，不声称已完成该固件适配。

## 当前解耦审查与仍存的依赖

| 范围 | 代码事实与边界 |
| --- | --- |
| 运行与管理 | `apps/`、`packages/` 没有 AlwayRoute 导入、RPC、SSH 或 UCI 调用。配置、订阅、核心控制、管理员凭据和会话均由 Coproxy 本地实现；不读取 AlwayRoute 的节点或账户 |
| 安装与发行 | `packages/deployment` 只校验并安装本地 Linux 载荷、服务和权限。发行包含 Coproxy、固定 Mihomo 和管理运行文件，不需要打包或安装 AlwayRoute，也不代改路由器配置 |
| 自动网关配置 | `packages/gateway/profile.ts` 校验网络角色字段，没有 AlwayRoute 产品字段；`host-plan.ts` 与 `apps/gateway/network.py` 实施来源/MAC、DNS、回程及网络归属要求。这些是当前交付方式的真实依赖，其他路由器必须满足 |
| 状态与控制 | Coproxy 报告自身核心事实，终端路径仍独立标记未核验。AlwayRoute 的 revision、job、operator 观察、DNS 预检及开关字段属于该可选适配器，不是 Coproxy 的必需接口 |
| 文档与验收 | 过去架构文档直接写成“AlwayRoute负责”，容易被理解为产品绑定，现改为协同路由器角色。真实终端验收目前仍主要来自该适配器组合；这是一项证据覆盖限制，不能推导其他原厂固件已验收 |
| 本地联调工具 | 个别私有 SSH、设备安装和参数映射脚本用于当前开发环境，不是发行内容或产品启动条件，不应复制到通用部署步骤 |

因此，当前没有需要先安装 AlwayRoute 才能启动 Coproxy 的运行依赖；仍依赖的是**能够满足当前交付契约的路由器配置**。针对其他实现，还需要完成能力映射及实际终端验收。现有软件也未提供自动配置任意厂商路由器、探测全部能力或一键管理第三方路由器的功能。

## 选型与验收结论如何记录

选型记录至少包含：外设系统/架构及资源余量；路由器固件版本和可用组件；交付、DNS、来源保留、排除、回程、IPv6、故障、独立关闭和持久行为的逐项依据；当前单终端范围；实际验证结果与未验证项。

只有能力表及该版本组合的实际验收都通过，才记为“该组合可用”。原厂固件能力满足但尚未测试时，记为“可进入验证”；关键能力缺失时，记为“当前方式不适用”。产品独立性不等于无条件硬件兼容，也不要求以固定设备清单取代能力判断。
