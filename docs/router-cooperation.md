# 与接入路由器的协作

状态：协作语义 v1，2026-10-25；已完成 ARM64 Linux 与已适配接入路由器的一台真实终端联合验收，范围见第 6 节。本文说明 Coproxy 的责任和外部依赖，不记录个人设备、真实网络拓扑或路由器内部控制实现。

## 1. 通用协作要求与本机联调资料

本文保存 Coproxy 侧的通用协作要求。Coproxy 独立安装和运行，协同路由器按[协同路由器要求与说明](cooperating-router-requirements.md)提供终端接入、流量转交、DNS 协调及独立关闭能力。路由器硬件、固件和组件以能否满足这些网络行为为准，内部管理接口和配置字段由各实现自行定义。本文不代替本机联调记录或其他项目的变更授权。

当前网络拓扑、真实设备与地址、接线、访问方法、调试输出和环境专用脚本属于本机资料。共同资料维护在双方仓库之外的一份共享目录中，各项目通过被忽略的目录链接 `.local/lab/shared/` 直接读取共享目录的导航和环境文件。真实路径不进入正式文件，项目独有资料继续留在自己的 `.local/`。

目录链接只提供资料入口，不会自动迁移旧内容、运行脚本或替换现有工具配置。链接缺失、失效或共同环境信息未核验时应明确提示，不猜测替代。

路由器模式切换与回退的内部机制不在本仓库记录。既有路由器管理 RPC 和上游核心 API 均不能自动视为跨项目接口已经存在。

联调前应确认必要的接口含义，记录双方明确的源码提交、组件版本及验收范围，不依赖两个分支的最新版恰好兼容。实际环境与原始记录保持私有；文档或提交只在本地存在时，不把它描述成远程已发布。

## 2. 职责与逻辑路径

| 角色 | 责任 |
| --- | --- |
| 接入路由器 | 终端接入、基础网络、受管终端范围、把流量交给网关和独立管理入口 |
| Coproxy 网关 | 收到流量后的透明接管、DNS 与分流、节点及订阅、代理出口连接和自身状态 |
| 上级网络 | 为经许可的出站连接提供外部可达路径 |

命中代理规则时，原终端流量先由接入路由器交给 Coproxy；Mihomo 再建立或复用到远端代理节点的连接，经同一台路由器 WAN 访问上级网络，节点再连接目标网站。响应经节点、路由器、Coproxy、路由器回到终端。路由器在 LAN 侧负责交付、WAN 侧负责外部出口，两次处理的是不同连接／会话。

完整的请求、响应、防循环、WAN NAT、规则直连和 DNS 路径见[终端访问公网的数据流与时序图](traffic-flow.md)。这些是产品角色关系，实际接线、接口和地址由部署输入决定。

Coproxy 不直接修改协同路由器配置，不以匿名健康检查触发设备动作，也不同时充当第二个路由器配置负责者。主机自身代理成功只能验证局部路径，不能替代终端接管验收。

## 3. Coproxy 需要满足的协作条件

- 接管方式与内核能力匹配，明确入口、受管来源、出口和排除范围；核心出站不再次被接管，数据与回程一起验证。一个网口也可承载不同阶段，但不能据此跳过连接跟踪和同接口路径检查。
- 优先维持终端网关和 DNS 入口的稳定性；网关接收路由器交付的解析请求，基础解析不得循环依赖该请求链。本地域名和管理访问不被破坏。
- TCP／UDP 和地址族分别声明支持范围；加密 DNS 和普通 DNS 分开评估，未知或未接管能力不伪报为支持。
- 区分服务就绪、配置应用、节点检查与终端实际出口；报告新鲜度和运行代次，不用过期快照确认新的配置。
- 管理身份、访问地址、接口和端口均为受控部署输入。原始凭据和实际环境数据不写入公共状态或版本契约。
- 网关只能确认自己的服务及检查结果，不能以自己停止或重启推导路由器已完成相应操作。双方部分完成时保持真实状态，故障边界须在共同约定确认后验证。

## 4. 联调和发布流程

1. 先确认通用职责、状态、兼容与验收要求；涉及运行环境的信息通过本地共享入口读取并核验，其他项目的代码、配置或设备变更仍需相应授权。
2. 各自完成对应模块与针对性检查；实际接入前确认路由器端已经具备所需管理和恢复能力，不能只因 Coproxy 就绪就扩大范围。
3. 只接入一台测试终端，按双方确认的联合清单验证协议、DNS、回程、故障和重启；具体路由器操作须在其项目范围内另行授权。
4. 正式结论只记录必要的脱敏条件、双方提交、组件版本及支持范围。仓库自身的原始材料按 AGENTS.md 放在 `.local/`；共同材料通过共享入口维护，不复制进正式文档或各自重复保存。
5. 在已验证组合上扩大终端范围；软件可独立升级，只有共同约定和能力要求变化时才需要另一端配套升级。未通过组合不宣称兼容。

实际测试入口、凭据与环境配置不跨仓库复制为正式内容；不要为联调建立必须依赖某台电脑目录的链接。本文与[项目方案](project-plan.md)共同定义 Coproxy 侧的工作范围，不代替对方项目作设计或实施决定。

## 5. 首轮共同语义 v1

- 范围为一台明确来源的终端、IPv4 TCP/UDP、真实地址 DNS；未支持的公网 IPv6 在受管范围阻断，本地控制与管理保留。终端默认网关和 DNS 入口仍为接入路由器。
- 路由器交付原终端源地址，Coproxy 确认受管来源和排除范围；新建出站连接经路由器 WAN，回程经路由器。网关自身出站不能再次被交付；同 LAN 的 MAC、回程、连接跟踪和原样转发防护须实测。端间不增加 SNAT 掩盖路径问题。
- 路由器分别配置链路接口、路由器/网关地址与网关 MAC、测试终端 IPv4/MAC、额外目的 CIDR 例外、网关 DNS 端口及专用 DNS 监听。本机实际值只留在本地资料；这些输入不是 Coproxy 自动修改路由器的接口。
- Coproxy 提供受限的 UDP/TCP DNS，网关 bootstrap 独立。路由器只把选中终端的公网解析送往该入口，本地域和无点名称保留基础解析，不切换所有终端共用上游。DoH/DoT 单独作为业务流量验证。
- 故障策略已经确认：开启后核心、DNS 或链路故障时阻断受管外网流量，保留开启意图并提示异常；用户手动关闭后恢复普通直连，不自动降级。初次开启预检失败保持原状态。
- 分别报告保存版本、期望启用状态、应用版本、核心/接管/DNS 状态、配置代次、错误和观测时间；路由器配置版本与 Coproxy 配置代次分别核对。字段名称和状态存储方式由各实现定义，就绪不能推导真实终端出口已经验收。
- 已验收组合的日常应用可由路由器向配置的网关 DNS 发起有界的新鲜 UDP 查询，预检失败保持原状态，成功后应用受管交付。该检查只证明 DNS 可达；未独立观察的核心、来源、出口与回程如实标记未核验。新的应用须重新查询，状态缓存须报告观察时间和有效期，不能用过期结果确认本次应用。具体超时、缓存时限和人工观察入口由路由器实现定义。
- 路由器重启或状态重建时，应先恢复受管外网阻断；重新启用交付前执行新鲜预检。独立关闭须在网关离线或观察信息不可用时仍可完成。当前不提供自动恢复代理交付的承诺。启动早期、重载及规则清空期间的连续阻断须单独验收，当前证据尚未覆盖全部路径，限制见[发行说明](release-notes.md)。
- Coproxy 原生自动网关已接入编译、事务、受限运行和网络前置单元；核心停止保留独立 guard。显式代理模式仍不提供透明网关能力。未验证的状态如实标记，不使用测试替身向路由器伪报就绪。

兼容性以当次双方提交、安装版本及验收范围确认；语义 v1 对齐不表示所有设备组合或全部后端字段已经验收。

## 6. 已验证范围与后续关卡

首轮实际链路使用 Mihomo v1.19.33、Coproxy `3a91b99` 和一个已适配的协同路由器组合。操作者确认受管手机浏览器可以访问代理及普通站点；核心停止后新的代理请求失败，核心仍停止时从接入路由器关闭交付后新的普通网页恢复。头部和核心元数据观察支持原终端来源到达网关、TCP／UDP 进入核心、出站及终端回程经过接入路由器；未观察到终端回程绕过接入路由器。网关 DNS 的真实 UDP／TCP 查询均成功。该记录不包含业务载荷，也不把被动观察等同于所有 UDP 应用均已验收。

该路由器组合另通过真实系统上的 DNS 预检应用、重复应用、超过短期观察窗口后的状态、状态重建后重新应用，以及核心离线时独立关闭。管理 HTTPS 的登录、会话和访问边界已在实际服务验证，终端浏览器的证书确认及管理操作仍是独立验收步骤。

现成适配示例：AlwayRoute 的 `feat/external-proxy` 分支已集成上述流量转交、DNS 协调和独立关闭能力；首轮使用 forwarding r4，后续路由器侧验证版本为 `d54167e`。它提供特定场景下的路由器侧实现，Coproxy 的安装和运行不依赖该项目；其他固件或组件按同样能力要求配置并分别验收。

隔离网络覆盖 TCP／UDP、DNS、核心退出／恢复和交付撤销；它不能替代多终端、真实 UDP 应用、系统重启、长时间运行、其他 CPU／内核及路由器固件组合的验收。当前双方受管来源模型限定一台 IPv4 终端；扩大范围须同时实现并验证两端配置与故障隔离，不能直接把单个地址替换成整个 LAN。
