# 终端如何通过路由器和外接代理设备访问公网

本文解释当前原生透明网关的完整业务路径。文中只使用受管终端、接入路由器、外接代理设备、代理节点和目标网站等通用角色，不把某台设备或个人网络作为产品前提。软件模块和进程关系见[软件架构](architecture.md)，两侧网络要求见[协同路由器说明](cooperating-router-requirements.md)。

## 1. 先区分五个角色与三段连接

| 角色 | 是什么 | 在本次访问中的作用 |
| --- | --- | --- |
| 受管终端 | 手机、电脑等客户端 | 发起原本要访问目标网站的请求；默认网关仍为接入路由器 |
| 接入路由器 | 终端接入的网络路由器 | LAN 侧选择并交付受管流量，WAN 侧为代理设备提供外部可达路径；同一台设备承担两种职责 |
| 外接代理设备 | 独立运行 Coproxy 的 Linux 主机 | Mihomo 接收交付流量、按规则分流，建立或复用到代理节点的出站连接 |
| 代理节点 | 配置中选定的远端代理服务 | 接收 Mihomo 的代理协议连接，代表该业务访问连接目标网站 |
| 目标网站 | 浏览器最终要访问的业务服务 | 接收代理节点发起的连接并返回业务响应 |

最关键的区别是：**终端原始访问、Mihomo 到代理节点的连接、代理节点到目标网站的连接是不同的连接／会话**。同一个 IP 包并不是原样绕过所有角色；Mihomo 将终端访问交给出站协议承载，节点再与目标服务通信。TCP、UDP 和协议复用方式不同，不能据此认为每个网页请求都会新建一条 TCP 连接。

代理设备不用另有一条独立互联网线路，也不要求物理串在路由器与上级网络之间。当前模式中，它可以从同一个网络接口接收路由器交付的原始流量，再从该接口把代理出站交回路由器；路由器继续通过自己的 WAN 访问上级网络。具体物理接口和连接方式由部署决定，不能从角色图推导某个无线或有线连接已被使用。

## 2. 命中代理规则时：请求与响应的完整过程

![终端、同一台接入路由器、外接代理设备、代理节点和目标网站之间的请求及响应时序](images/proxy-traffic-flow.svg)

每列表示同一角色，时间从上往下推进。横向箭头表示该步骤的传递方向，竖虚线只是角色的时间线，不表示另一条链路或数据流。图中上级网络折叠在第 ④⑦ 步中，不把运营商或上级路由器画成 Coproxy 自有模块。

### 请求怎样出去

1. **终端先把访问交给接入路由器。** 终端的业务目标仍是网站；路由器是默认网关／下一跳，并不意味着网站请求的目的 IP 就变成路由器管理地址。
2. **路由器把受管流量交给外接代理设备。** 路由器按来源和入口等条件选择受管终端，保留原终端源 IP，将该段流量交付外设。Coproxy 通过 Linux 入口、独立 guard 和 Mihomo TUN 接管原始访问，再匹配规则和策略组。
3. **Mihomo 将访问交给选中的远端代理节点。** 对代理规则，核心建立或复用以代理节点为远端的协议连接；这段出站的本机端是代理设备，和第 ② 步的原终端流量不同。核心绑定部署接口，并以固定部署标记选择出口，下一跳明确指向接入路由器。
4. **同一台路由器把这段代理出站送向 WAN。** 路由器将外设出站按正常外部路由发往上级网络，再到代理节点。上级网络可以包含其他路由器或运营商网络；WAN 地址转换按部署环境进行。这里不把它再次当作受管终端的原始流量交回外设。
5. **代理节点访问目标网站。** 节点处理代理协议，并建立到目标网站的业务连接。接入路由器为本地代理设备提供到节点的网络通路，不负责解码代理协议。对于 HTTPS 网站，代理承载浏览器与网站之间的 HTTPS 数据，不等于代理设备自动解密了网站 HTTPS 内容。

接入路由器因而出现两次：第一次承担 **LAN 侧的终端流量交付**，第二次承担 **WAN 侧的代理连接出口**。它始终是同一台路由器，处理的流量身份和方向不同。

### 响应怎样回来

6. 目标网站将响应返回代理节点。
7. 节点沿已有代理连接返回，经上级网络到达接入路由器 WAN；涉及 NAT 时由相应连接跟踪恢复对应映射。
8. 路由器把这段代理连接的回包交回外接代理设备。
9. Mihomo 处理代理协议，并向原终端会话交付业务响应。当前实现通过终端 `/32` 回程路由，将这段响应先交给接入路由器。
10. 路由器经 LAN／Wi-Fi 将响应交给原终端。即使终端与外设同属一个子网，也不能在当前交付方式下假定外设直接返回终端即可；同接口转发、连接跟踪和回程须一起满足。

因此，向外和回来的每个方向，都要分别区分“原终端会话”和“代理设备的出站会话”。响应先回代理设备处理，再经路由器回终端；不能省略代理设备直接把代理节点回包当成网站回包交给终端。

## 3. 为什么不会在路由器与代理设备之间循环

防循环来自两侧明确的流量分类与路由，不是依靠“同一个包已经走过一次”的猜测：

| 流量类别 | 当前要求的处理方式 |
| --- | --- |
| 受管终端的原始公网 TCP／UDP | 路由器按来源与入口选择，交付代理设备；路由器到外设这段不做 SNAT／masquerade 来隐藏终端来源 |
| Mihomo 发起的代理节点连接或规则直连 | 以外设为本机端，经核心部署标记、专用出口表和绑定接口交给路由器；路由器排除这类出站，不再交回外设 |
| 代理连接回包 | 按实际连接状态回到外设，不当作新的终端原始访问 |
| 核心返回终端的响应 | 外设通过终端 `/32` 路由先交给接入路由器，再由路由器送给终端，不再次交回外设 |
| 代理主机上其他本机应用 | 通过 UID 排除保留原有主机出口，不因处理终端流量就接管整台主机；这与 Mihomo 自身带标记出站是不同边界 |

**不在路由器到外设的交付段做 SNAT，与 WAN 可以保留原有 NAT 并不矛盾。** 前者保护终端身份，后者解决外部网络需要的地址转换；代理设备的路由标记是本机策略选择依据，不要求上游路由器读取这个标记。

核心配置依据见 [`profile.ts`](../packages/gateway/profile.ts) 的 `interface-name`、`routing-mark`、原生 TUN 与 UID 排除；出口和回程依据见 [`network.py`](../apps/gateway/network.py) 的 `route_args`、`rule_args` 和 `capture_args`。路由器侧仍须满足[下一跳、防循环及连接跟踪要求](cooperating-router-requirements.md)，不能把自己的全局默认路由一律改成外设来代替这些条件。

## 4. 规则直连、关闭代理和 DNS 分别怎么走

| 场景 | 路径及区别 |
| --- | --- |
| 已开启交付，命中代理规则 | 终端经路由器到 Coproxy；Mihomo 的代理连接经同一路由器 WAN 到代理节点，再由节点访问网站；响应按图返回 |
| 已开启交付，命中 `DIRECT` 规则 | 原始流量仍先交给 Coproxy；Mihomo 直接连接目标网站，出站仍经接入路由器 WAN，不使用远端代理节点；响应先回核心再回终端 |
| 用户从路由器关闭交付 | 路由器撤销交付并恢复相应 DNS；终端通过路由器正常上网，不再经过外设处理 |
| 仍处于开启状态，但外设、核心或链路故障 | 阻断受管外网，保留开启意图；不能把它解释为自动恢复普通直连 |
| 受管终端的普通公网 DNS | 终端先查询路由器，路由器只将选中终端的公网解析转交 Coproxy 的受限 DNS，再由其使用部署配置的解析上游；DNS 响应按相应请求路径返回 |
| 本地域名／基础解析与 bootstrap | 本地域名由路由器保留处理；核心 bootstrap 不能循环依赖自己尚未建立的受管解析链。DNS 上游并不因此等同于代理节点 |

本图只画一条命中代理规则的业务访问，不把 DNS 解析混入同一套十步编号。DoH／DoT 属于另外声明和验证的业务流量，不能把普通 DNS 转交等同于已接管所有加密解析。

## 5. 阅读与验证边界

以上是当前原生网关的角色关系和实现要求，不代表每个新设备组合都已实测。受管范围目前为一台明确的 IPv4 终端，公网 IPv6 按两侧约定阻断；多终端、整机重启、其他固件和硬件仍需独立验收。

真实路径验收至少分别确认：原终端来源到达外设、核心代理连接经指定路由器 WAN、代理回包回到外设、终端回程经路由器、未形成再次交付循环，以及核心故障阻断和路由器独立关闭。核心状态、管理页面可访问、单机代理成功，都不能代替这些路径事实。正式验证范围见[路由器协作](router-cooperation.md)，安装前提见[部署说明](deployment.md)。
