# Coproxy 软件架构

本文记录开发方向；实现进度见 development.md。当前已实现离线配置、版本化草稿、订阅节点快照、事务状态机和 CLI，以下管理与网络模块仍待集成验证。

## 模块与唯一归属

| 模块 | 职责 | 当前状态 |
| --- | --- | --- |
| packages/config | 部署边界、用户策略和离线节点快照编译，生成内容代次 | 已实现 |
| packages/drafts | 保存草稿、修订号 CAS 和私有输入捕获，与应用状态分离 | 已实现 |
| packages/subscriptions | 来源修订号、受限 HTTPS、节点快照和失败保留，刷新提交时再次 CAS | JSON 节点快照与 CLI 已实现，待上游 YAML 适配 |
| packages/transaction | 私有存储、并发冲突、应用提交点和中断恢复 | 状态机已实现，缺真实运行适配器 |
| packages/mihomo | 调用指定核心进行有界、脱敏语法校验 | 包装器已实现，缺真实核心验收 |
| apps/cli | 编译、校验、候选暂存与只读状态 | 已实现 |
| 管理服务与界面 | 复用 MetaCubeXD 的界面和 Agent 能力 | 已审查适配点，未集成 |
| 网络执行服务 | 受管来源、TUN 路由、出口、防护和资源恢复 | 待实现 |

全部配置应用由同一事务入口负责，订阅更新、网页编辑和后台任务不能分别改写运行配置。systemd 是拟定的核心唯一监管者；接入上游时适配其 supervisor，不保留第二条自动拉起路径。管理后端只申请受限的生命周期操作。网络执行服务是本端自有 nft 和策略路由资源的唯一管理者；若采用核心自动网络机制，必须重新明确资源归属，不能同时管理同一资源。

## 配置与运行

配置分为受保护部署参数、用户策略、来源快照和编译代次。来源不能覆盖接管、认证、监听和出口边界，所有合法高级字段由选定核心继续校验。首批输入仅支持 JSON；未来上游 YAML 编辑与订阅转换在边界明确的适配层处理，不执行来源脚本。

先暂存不可变候选，再进行核心校验、网络预检、持久化应用、就绪确认和提交。失败恢复上一确认状态；恢复失败保留事务和故障，不宣称已应用。运行适配器必须自行有界并在失败后停止副作用，避免尚未结束的激活与回滚并行。历史提交成功不等于当前核心、接管或终端出口健康。

## 网关与外部协作

首轮只交付 IPv4 TCP/UDP 和真实地址 DNS；TUN 为优先验证方向。在共享主机上先验证范围明确的入口、来源路由与出口策略，保护管理和原有构建任务。核心原始接管、核心新建出站与返回终端的响应分别验证。未接管流量不能使主机退化成普通旁路转发器。同 LAN 回程不能默认成立，若无法满足连接跟踪和隔离要求，再评估独立三层链路。

AlwayRoute 负责受管来源、外部代理开关、基础网络和独立关闭恢复。Coproxy 只负责收到流量后的接管、DNS、分流与自身状态，不写路由器配置。首轮通过本地诊断对齐必要语义，再按实际缺口增加带认证的最小只读接口。

本地域名由路由器处理，受管公网解析交给受限 Coproxy DNS；bootstrap 不经过同一转发循环。单终端阶段不能替换所有终端共用的解析路径。加密 DNS、来源丢失后的设备策略和未支持地址族单独声明能力。

按[首轮协作语义 v1](router-cooperation.md)，开启后的核心、DNS 或链路故障采用受管外网阻断，保留开启意图，用户关闭后恢复直连，不自动降级。首轮使用人工本地诊断；路由器的 operator 观察须匹配目标、请求 revision 和网关 generation，并在 30 秒内使用。重启先恢复阻断，重新观察后再显式应用。当前离线模块不提供这些网关就绪事实，不能作为该观察的替代物。
