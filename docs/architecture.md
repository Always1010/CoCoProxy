# Coproxy 软件架构

本文记录模块边界与开发方向；验证方法和范围见 development.md。当前已完成回环显式代理、管理网页与受控事务的集成源码，固定核心及六种协议已通过真实回环检查。systemd 服务尚未安装，网络接管与跨设备路径仍待实现和验收。

## 模块与唯一归属

| 模块 | 职责 | 当前状态 |
| --- | --- | --- |
| packages/config | 部署边界、用户策略和离线节点快照编译，生成内容代次 | 已实现 |

| packages/subscriptions | 来源修订号、受限 HTTPS、节点快照和失败保留，刷新提交时再次 CAS | JSON 与管理端 Clash YAML 节点解码已实现 |
| packages/transaction | 私有存储、并发冲突、应用提交点和中断恢复 | 已接运行适配，管理启动等待一次恢复；真实 systemd 事务待验收 |
| packages/runtime、apps/runtime | systemd 唯一监管、部署计划、exec 启动与进程/控制端口就绪 | 已实现源码及 Linux 夹具验证，未部署服务 |
| packages/mihomo | 调用指定核心进行有界、脱敏语法校验 | 固定核心语法、HTTP／DNS／控制器及六种协议回环已验证 |

| packages/network 与网络执行服务 | 受管来源、TUN 路由、出口、防护和资源恢复 | 纯资源／阶段计划已实现；核心配置、特权执行者和内核验收待接入 |

全部配置应用由同一事务入口负责，订阅更新、网页编辑和后台任务不能分别改写运行配置。运行适配选择 systemd 为核心唯一监管者，启动器直接 exec 替换自身；接入上游时适配其 supervisor，不保留第二条自动拉起路径。管理后端只申请受限的生命周期操作。网络执行服务是本端自有 nft 和策略路由资源的唯一管理者；若采用核心自动网络机制，必须重新明确资源归属，不能同时管理同一资源。

## 配置与运行

配置分为受保护部署参数、用户策略、来源快照和编译代次。来源不能覆盖接管、认证、监听和出口边界，所有合法高级字段由选定核心继续校验。策略高级编辑使用 JSON；管理服务在受限解码器中接受 JSON／Clash YAML 来源并只提取节点，不导入来源规则、部署或脚本。核心 HTTP 与实时流固定经同源受限代理，浏览器不直接持有 controller secret。

先暂存不可变候选，再进行核心校验、网络预检、持久化应用、就绪确认和提交。失败恢复上一确认状态；恢复失败保留事务和故障，不宣称已应用。运行适配器必须自行有界并在失败后停止副作用，避免尚未结束的激活与回滚并行。历史提交成功不等于当前核心、接管或终端出口健康。

## 网关与外部协作

首轮只交付 IPv4 TCP/UDP 和真实地址 DNS；TUN 为优先验证方向。在共享主机上先验证范围明确的入口、来源路由与出口策略，保护管理和原有构建任务。核心原始接管、核心新建出站与返回终端的响应分别验证。未接管流量不能使主机退化成普通旁路转发器。同 LAN 回程不能默认成立，若无法满足连接跟踪和隔离要求，再评估独立三层链路。

[网络资源契约](../packages/network/README.md) 将单终端输入、固定资源归属、mark 保留位、三张带黑洞默认的路由表、受限 DNS、经路由器的出口／回程、持久 guard 和故障阻断编成确定摘要计划。先阻断，再准备资源，最后依据同代核心、TUN、DNS、cgroup 与路由证据激活；不能按共享服务 UID 放行核心出口。该模块尚未生成可执行规则，也未挂接事务或管理入口，输出中的接管与终端路径仍是未验证。

AlwayRoute 负责受管来源、外部代理开关、基础网络和独立关闭恢复。Coproxy 只负责收到流量后的接管、DNS、分流与自身状态，不写路由器配置。首轮通过本地诊断对齐必要语义，再按实际缺口增加带认证的最小只读接口。

本地域名由路由器处理，受管公网解析交给受限 Coproxy DNS；bootstrap 不经过同一转发循环。单终端阶段不能替换所有终端共用的解析路径。加密 DNS、来源丢失后的设备策略和未支持地址族单独声明能力。

按[首轮协作语义 v1](router-cooperation.md)，开启后的核心、DNS 或链路故障采用受管外网阻断，保留开启意图，用户关闭后恢复直连，不自动降级。首轮使用人工本地诊断；路由器的 operator 观察须匹配目标、请求 revision 和网关 generation，并在 30 秒内使用。重启先恢复阻断，重新观察后再显式应用。当前离线模块不提供这些网关就绪事实，不能作为该观察的替代物。
