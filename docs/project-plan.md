# 项目目标与技术方案

状态：方案与实施边界，2026-10-25；开发进度见[开发与验证说明](development.md)。配置、事务、管理网页和固定显式发行已通过实际服务验证；六种基础协议及 VLESS REALITY 已通过真实回环检查。首轮网关使用 Mihomo 原生自动接管，保留必要 guard、出口与回程集成；旧自研网络框架作为对照保留。ARM64 已有实际安装、单终端浏览器代理、核心故障阻断、独立关闭恢复及手机管理登录证据；重启、负载、其他协议变体与设备组合仍须独立验收。初始平台优先 Linux ARM64，其他架构按发行资产与实际验证扩展。

## 1. 项目目标与范围

构建可长期运行、通过网页维护的局域网代理网关，管理节点、订阅、规则、DNS、运行状态与配置应用。接入路由器把明确范围的终端流量交给网关，由网关按策略处理。整体职责见[路由器协作](router-cooperation.md)。

Coproxy 是独立的代理解决方案，拥有自己的安装载荷、配置、服务、账户及网页入口。协同路由器通过符合要求的硬件、固件或组件提供流量转交能力，不把 OpenWrt、特定路由器型号或某台外接主机作为产品前提。外设当前运行条件、协同路由器能力表及两端部署路径见[协同路由器要求与说明](cooperating-router-requirements.md)。独立部署不代表任意硬件可运行，也不代替路由器交付和真实终端验收。

- 优先采用成熟开源核心与管理系统；只开发明确的集成和可靠性缺口，不自行实现代理协议或密码算法。
- 软件能力不受旧项目的配置模型限制，也不预设必须采用某一个核心；以节点兼容、管理完整性、稳定性和维护成本确认选型。
- 不要求更换主机操作系统，不把桌面系统代理等同于局域网接管；先在明确授权的现有 Linux 环境验证服务部署。
- 路由器侧的具体机制由协作项目维护；本仓库只负责网关软件及其协作边界。

## 2. 开源选型与决策边界

本节保留早期候选比较及选型原则。**当前已实现的是 Mihomo v1.19.33 + 经 Coproxy 适配的 MetaCubeXD v1.273.1 UI／Nitro Server**；原 Agent 的核心监管与刷新应用入口已禁用，由自有管理事务和 systemd 承接。表中的其他方案不表示已经集成，sing-box 仅另用于协议回环测试。当前组件、版本、进程和调用关系见[软件架构与总览图](architecture.md)。

| 候选 | 本项目中的定位 | 确认前必须检查 |
| --- | --- | --- |
| Mihomo＋MetaCubeXD Server／Agent | 早期首选组合；核心、管理界面和配置管理分层评估 | 真实节点参数、订阅与编辑能力、Linux 接管、认证、配置失败处理和版本匹配 |
| v2rayA | 完整服务对照，若已满足关键需求可直接采用 | 配套核心约束、规则表达、管理流程、透明接管和实际网络兼容性 |
| sing-box＋官方 Dashboard | 有力备选，不因既有项目使用过而默认选择或排除 | 所选版本的协议与 API、管理流程、配置迁移和网关行为 |
| ShellCrash | 部署、更新、转发模式与运维流程参考，也可用于独立验证 | 与选定管理者的配置和生命周期边界，避免重复管理同一核心 |
| dae 及其管理生态 | 性能与接管方式的后续候选 | 内核条件、管理项目维护状态、协议兼容和代表负载；不将 eBPF 名称当作性能保证 |
| 面向路由器系统的插件组合 | 另一种专职网关部署路线的参考 | 系统依赖与迁移范围；不假定能原样运行在通用 Linux 发行版 |

选型阶段记录的正式版本评估起点包括 Mihomo v1.19.33、MetaCubeXD v1.273.1 和 v2rayA v2.5.10；当时尚未形成已验证的组合或版本锁。后续实施已对固定 Mihomo、适配后的 MetaCubeXD 和相应资产形成审阅与装配记录，当前依据见[软件架构](architecture.md)。后续变更版本仍须核对来源、发行架构、依赖、校验信息与兼容性，并在运行验证后更新可复现锁定。

Mihomo 的 provider、策略组和 API 生态与多来源规则管理相匹配，是首选理由；不据此宣称其性能优于其他核心。MetaCubeXD 的纯静态面板与 Server／Agent 能力不同，不能只部署静态页面就宣称具有配置管理。v2rayA 当前要求其程序与配套核心版本匹配，不把任意上游核心替换视为受支持组合。

首次只选择一个主要运行核心；只有经证实的功能缺口才引入额外核心。不为展示功能数量同时维护多套协议转换与运行配置。

## 3. 建议架构

下表描述选型阶段的分层方向；当前落地使用适配后的 UI／Server、自有配置管理和 systemd 唯一核心监管，不原样运行上游 Agent。具体结构和源码对应以[当前架构](architecture.md)为准。

| 层次 | 首选实现方向 | 责任 |
| --- | --- | --- |
| 代理核心 | 官方正式 ARM64 核心 | 协议、加密、连接、DNS 和分流 |
| 管理系统 | 选型阶段建议评估 MetaCubeXD Server／Agent 或完整替代方案；当前采用适配后的 UI／Server | 节点、订阅、配置编辑、选择、连接与状态 |
| 网关集成 | 核心接管机制与必要的自有集成 | 指定终端流量接管、出口约束、管理通道保护和就绪状态 |
| 系统运行 | 原生 Linux 服务，优先 systemd | 启动、进程监管、日志限制、版本及配置恢复 |

原生服务仍需要构建管理组件、整理运行依赖及打包；上游提供源码不代表已有符合本项目要求的安装包。容器可作为另一发行形态，但透明接管必须单独验证宿主网络、权限、设备访问和生命周期；普通端口映射不等于完整网关。

接管首选评估 TUN，使用所选稳定版本支持的自动路由和重定向能力，明确受管来源及出口；协议栈先采用该版本的适用基线，再按实际兼容和负载比较。配置名称或自动探测成功不替代单终端 TCP／UDP、DNS 和回程验收。参考 [Mihomo TUN 文档](https://wiki.metacubex.one/en/config/inbound/tun/)，实施时仍须核对对应版本，不能照抄最新分支的新选项。

系统服务分别监管管理后端和核心；管理后端通过唯一事务入口申请受限的核心 start/stop，不能再保留 Agent 自行拉起核心的 watchdog。网络规则也须有明确的唯一归属，避免核心自动接管与外部脚本重复设置。

## 4. 功能目标

| 范围 | 初期交付目标 | 后续扩展 |
| --- | --- | --- |
| 协议 | 按真实需求验证常见 VMess、VLESS／REALITY、Trojan、Shadowsocks、Hysteria2、TUIC 等输入 | 其他协议与传输变体按所选版本和实际节点逐项接入 |
| 节点与订阅 | 多来源、手动节点、分组、更新失败保留可用数据 | 去重、覆盖、批量编辑和使用量 |
| 分流 | 域名、地址、服务与受支持的设备策略，明确默认出口和优先级 | 自动选优及更细业务策略 |
| DNS 与接管 | 接管范围、解析路径、回程和未支持范围可解释 | 经验证的双栈与应用兼容增强 |
| 管理 | 认证、保存／应用区分、状态、连接、流量与脱敏错误 | 有限期历史和按设备统计 |
| 维护 | 启动恢复、配置校验、失败恢复、受控升级 | 网页内升级与更多发行架构 |

核心声明、管理界面可配置与终端实际可用分别验收。表单之外保留可校验的高级配置入口，不在保存时静默删除未被表单识别的合法字段。

按设备分流不等于识别任意终端应用进程；连接级负载均衡不等于给单个连接叠加多节点带宽。性能与协议能力都不按主机资源或功能列表推算。

## 5. 可靠性与配置原则

- 本项目掌握的接管、监听、认证和出口配置与订阅内容分离；来源更新不能覆盖受保护的管理与网络边界。导入不执行来源附带的任意脚本，不默认把真实订阅交给公共转换服务。
- 候选先校验，再有界应用并确认；失败保留或恢复上一份可用配置。保存成功、核心就绪和终端出口健康分别记录。
- 协调订阅更新、人工编辑和核心生命周期；处理版本冲突、并发及中断。不把上游语法检查等同于完整恢复机制已经满足。
- 网关故障时不擅自把本应代理的流量变成直连；只报告自己的事实，不向用户伪报接入路由器已完成其他动作。
- 管理入口有独立认证和网络访问限制，核心控制凭据不等于用户登录。日志、统计和缓存有容量与保留上限。
- 暂未接管的地址族不得形成绕行。普通 DNS、加密 DNS 和应用内解析分别评估；本地 DNS 与网关基础解析不能循环。
- 升级锁定受审阅版本与来源，校验输入并保留配置恢复能力；不默认跟随浮动最新版或预发布分支。

## 6. 实施阶段与分工

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| 环境预检 | 只读核对内核、接口、权限、端口、已有服务及依赖 | 明确兼容条件和需另行授权的变更；不把检查视为安装许可 |
| 候选对照 | 相同输入与路径下验证首选组合和完整替代方案 | 选定主要方案，记录缺口及版本，不长期保持两套生产管理者 |
| 网关最小闭环 | 配置生成、核心、DNS、状态与服务打包 | 网关自身可用，但不提前宣称局域网已接管 |
| 单终端协作 | 按确认的通用协作要求接入一台测试终端 | 数据、解析、管理与故障边界通过联合验收 |
| 可靠性与负载 | 更新、错误配置、退出、重启、网络重连和代表负载 | 记录实际资源、忙时延迟、吞吐和错误，完成必要修复 |
| 发行与增强 | 发布清单、部署说明和明确缺口的功能开发 | 形成经过验证的版本组合后再扩大接管范围 |

初期由主 Agent 串行负责选型、集成和网络联调；设备配置保持唯一操作者。独立代码任务出现后再决定是否委派，不并发修改网络。验证按改动范围执行，不为文档与可逆低影响改动堆砌测试。
