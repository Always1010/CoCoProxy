# 从另一台电脑部署与更新

这个入口随 Linux 发行包提供，部署时不需要开发仓库、构建工具链或特定设备。先从可信发行来源核对 SHA256SUMS，解压匹配目标架构的发行包，再在解压目录运行。它部署当前解压的版本，不自动下载“最新版本”。

```sh
./cocoproxy deploy 192.0.2.2 --check
./cocoproxy deploy 192.0.2.2
```

Windows 也可以直接使用发行包中的 Node 入口：

```powershell
node source/scripts/deploy-ssh.mjs 192.0.2.2
```

上述地址为合成示例。IP 是唯一必填位置参数；SSH 用户、端口和密钥由系统已有 SSH 配置提供，或使用 `--user`、`--port`、`--identity`、`--known-hosts` 显式指定。目标的不同接口共用已核验主机身份时可显式指定 `--host-key-alias`。工具不会改本机 SSH 配置、自动接受未知指纹或忽略指纹变化。首次连接应先用原生 SSH 核验身份。目标需具有 Node.js ≥22.18、Python 3、systemd 及[部署指南](getting-started.md)所列运行工具、专用服务账户与网络前提；调用电脑需要 Node、OpenSSH 和 tar。工具不安装依赖或创建系统账户。

## 首次安装

IP 不能确定接口、路由器 MAC、LAN 范围、HTTPS、管理员身份或订阅许可。先按[安装配置说明](setup.md)准备私有环境 JSON、目标上的 HTTPS 证书与服务身份，以及仅用于首次初始化的私有管理员 JSON。然后运行：

```sh
./cocoproxy deploy 192.0.2.2 --user operator \
  --environment /absolute/private/environment.json \
  --admin-input /absolute/private/administrator.json
```

环境字段使用 `source/examples/setup-environment.json` 的合成结构。管理员文件包含 `username` 和 `password`，不得把真实值写进命令行、源码、发行包或公开日志。Unix 上输入必须是 0600 的单链接普通文件；Windows 上应使用仅当前用户可读的私有目录。SSH 非 root 用户通过目标上的 sudo 授权执行；交互终端可提示 sudo 密码，无终端自动化要求已有 `sudo -n` 权限。

入口核验清单中的文件，传输到专用临时目录，再由目标端公开安装器核验完整载荷、平台、权限、配置及安装归属。安装后初始化唯一管理员并启动管理服务；配置为受管 HTTPS 时也启动网页服务。不自动 enable、不导入订阅、不为路由器开启流量交付。首次应用和端到端验收继续按[部署指南](getting-started.md)完成。

## 后续更新

目标保存 `/etc/cocoproxy-install/deployment.json`，作为唯一的部署输入主本，权限为 root:0600、父目录 root:0700。新版本只更换 release、核心摘要和服务入口，保留网络、内部身份、凭据路径和业务状态。取得并核验下一版发行包后，再运行同一条 `cocoproxy deploy <IP>` 即可。

之前通过底层安装器部署的设备，首次使用此入口时传入原私有安装输入：

```sh
./cocoproxy deploy 192.0.2.2 --input /absolute/private/previous-deployment.json
```

它必须与已安装收据及实际配置一致，工具不凭 IP 猜测或接管手工安装，也不绕过配置审阅。自定义输入路径仍按原安装器验证。

自动网关更新需要先关闭协同路由器交付。内置 AlwayRoute SSH 适配器可使用下列参数文件；具体固件/组件版本的关闭与恢复流程仍须按[路由器契约](router-contract.md)验收，合成测试不代表该组合已经完成实体网络验收：

```json
{
  "host": "192.0.2.1",
  "user": "root",
  "port": 22,
  "identityFile": "/absolute/private/router-key",
  "knownHostsFile": "/absolute/private/router-known-hosts"
}
```

这些路径指向目标网关上原有的密钥与主机指纹文件，工具不会复制密钥。首次更新增加 `--router-config /absolute/private/router-ssh.json`，以后复用目标上的 root:0600 配置。适配器通过公开 ubus API 查询、关闭、等待任务并恢复原开启意图，不安装或更新路由器软件。异步任务轮询按 120 秒总时限计入 RPC 耗时，每次 RPC 最多 30 秒；协调器为包含前后状态核验的操作保留 300 秒上限，超时返回失败并要求审阅，不推断远端任务已经取消。其他协同路由器可配置 `--router-hook /absolute/root-owned/executable`：它须接受下述 `check-adapter`，以及 `status`、`disable`、`enable`；`status` 只返回 `{"enabled":true}` 或 `{"enabled":false}`，执行操作须等待结果确认。适配器及全部祖先须 root 控制、不可被其他身份写入。

自动网关已有安装在预览或开始维护前，先调用 `check-adapter`，再独立查询 status。内置适配器复用 enable 的能力/schema校验，最小返回格式为 `{"schemaVersion":1,"compatible":true}`；还提供 `scope:capabilities-and-readable-configuration-schema` 和 `endToEnd:unverified`，仅说明所需接口能力与配置 schema/revision 可读，不证明两端配置匹配、真实转发或恢复必定成功。候选 enabled:false 或 degraded 本身不阻止该兼容性观察；是否处于可维护状态仍由后续 status 等前置条件判断。

自定义 hook 也须实现该只读动作：检查自己的查询/独立关闭/恢复接口及兼容配置格式，失败或未知时非零退出或不返回 compatible:true。旧 hook 应先按本约定增加检查并单独运行，再重做 `--preview`；不能仅为过检固定返回 true。缺动作、不兼容、未知或结果格式不符均以 `REMOTE_ROUTER_ADAPTER_PREFLIGHT_FAILED` 在暂停、关闭交付或停服前拒绝，不静默跳过，也不要求为此先更改当前开启意图。

更新先在服务运行期间执行公开 prepare 检查，然后通过新载荷的公共维护命令持久暂停并排空事务、关闭路由器交付、停止服务并安全退役旧网络，再执行公开升级。安装完成后先凭本次指纹约束的令牌恢复原 runtime 标记，再启动服务；原来没有标记时恢复为缺失，持久恢复未启用时也保持原 flags，不把维护操作变成新的开启意图。已经启用但处于维护暂停的安装拒绝自动更新；停用且核心已停止的安装可以更新并保持停用。暂停标记与仍运行核心同时存在时须先人工审阅，入口不会为启动核心而临时放宽暂停。

准备检查拒绝继续时，标准错误先输出 `phase: "prepare"` 的简短 JSON，列出准备状态、配置是否变化及不通过项的原因码，再返回 `REMOTE_UPGRADE_NOT_READY_OR_CONFIGURATION_CHANGED`。该摘要不包含私有配置、文件路径或凭据；按原因码查看准备检查说明，拒绝发生在暂停或停服之前。

随后恢复原服务启用与活动意图，核验核心就绪、状态保留和可读性，最后才恢复原路由器意图。工具自动从原受管配置取得必要路径，使用服务 UID 读取状态；部署者不需要研究私有状态格式、手工挑文件或复制摘要。结果使用 `preservation` 的具体范围和分项结论，替代旧 `privateStatePreserved` 布尔量。首次安装没有旧基线，显示 `not-applicable`；同版本没有执行升级窗口时显示 `not-run`。

独立外部网页单元如需随维护暂停，可首次传入 `--web-unit cocoproxy-web.service`；受管网页自动纳入。不会改变原有 enable 状态、重启整机或自动回滚业务状态。

### 升级保留核验的三个时点

1. 暂停并排空事务、关闭路由器交付、停止管理与核心服务后，读取当前安装的基线。此时之前已经完成的合法编辑纳入基线。安装前若实际 reader 无法完整读取状态，或已提交 active 与持久 selection 不匹配、存在故障/待收敛事务，则停止升级并要求先恢复原配置事务；从未应用配置且两者均无记录不等于故障。
2. 新文件安装和收据核验完成、仍未恢复服务或 runtime 意图时，再读一次。比较管理员、规范已知状态文件、全部已存候选的存在集合及字节摘要，并比较状态与规范子目录的存在和目录项集合；新增、缺失和删除均不能以“剩余文件摘要相同”蒙混通过。这个停服窗口没有正常后台写入，任何差异都会阻止后续恢复并保留审阅记录。
3. 恢复原意图与服务、按原流程核验需要运行的核心后，再读一次。比较稳定身份与用户偏好，另列实际 reader 的完整内容可读性；不把恢复后的所有 JSON 原字节相同作为成功条件。取得这份结果后才恢复原路由器交付意图。

三次快照仅在协调进程内保留脱敏摘要，不复制凭据、数据库或订阅，不创建额外备份。读取会复核同名配置、凭据、订阅、候选与规范状态文件，并检查目录项一致；发生并发变动时要求重新审阅，避免混用不同代数据。报告只保存固定角色、原因码、范围与结果，不输出快照、真实设备标识、节点、订阅地址、推送私钥或 Cookie。

订阅和候选目录中的已知原子写入临时文件沿用原 Store 的命名规则跳过，不作为业务记录解析；目录项仍纳入停服窗口的一致性比较。其他未知文件、正式记录损坏或缺失仍拒绝继续。

| 结果范围 | 实际核验内容 | 正常运行后允许变化的内容 |
| --- | --- | --- |
| `contentChecks` | 复用实际 reader，完整验证字段、格式、持久候选摘要及按当前配置重编译 | 格式合法只证明可读，不单独证明安装未修改或业务可用 |
| `workspace`、`siteProbes`、`draft`、`subscriptions` | 用户策略、手动选择、自动选择设置、站点设置、草稿输入、订阅定义 | 修订/更新时间、订阅尝试时间和失败状态、刷新后的动态快照不冒充用户偏好 |
| `trusted-devices` | 尚未到期设备的身份、令牌摘要、信任范围和标签保留 | 合法续期可推进续期和到期时间；自然到期的记录可被清理 |
| `notifications` | 同身份绑定下已有 VAPID 密钥、订阅身份及偏好保留 | job、event、重试、发送结果及运行时间可正常推进；服务接受仍不证明终端显示 |
| `automatic-runtime-bindings`、`runtime-selection` | 运行绑定可由原 reader 读取，当前已提交 active、selection 与重新编译的候选一致 | 自动运行目标、事件、时间及热切换进程证据可变化；不宣称旧 PID 或同一动态目标永远保留，也不以格式可读代替策略重放 |
| `authentication` | 默认 `not-run`，未主动执行真实登录、Cookie 或终端推送测试 | 仍须按管理入口/终端验收检查实际可用性 |

`pass` 只覆盖分项声明的证据范围。安装窗口不同为 `REMOTE_PRESERVATION_INSTALL_WINDOW_CHANGED`，原意图及服务仍未恢复，保持路由器关闭并先审阅；恢复后稳定字段不同或无法取得一致读回为待审阅，返回 `REMOTE_PRESERVATION_READBACK_REQUIRES_REVIEW`，不能将其直接解释成安装破坏了状态。原配置事务需要恢复时返回 `REMOTE_PRESERVATION_RUNTIME_RECOVERY_REQUIRED`，先在后台/原运行入口审阅并恢复，再重新准备升级。已有失败记录仍会阻止盲目重试。

同 origin、同管理员凭据的正常升级应保持旧授权。若另行明确变更 origin 或管理员，原 reader 会按身份绑定使旧可信设备和通知授权失效；结果单列 `REMOTE_PRESERVATION_REAUTH_REQUIRED`，提示重新登录和重新订阅，不能将结构有效的旧文件当作损坏或强行保留旧授权。本远程更新仍只更换发行引用，不能用修改原输入绕过配置审阅来轮换身份。

网络回执为完整拥有状态时才调用旧版 helper 退役；从未启用或已经退役的网络不重复执行删除。回执不完整或在维护期间改变时停止并要求审阅。所有路径仍须通过公开安装器对实际网络资源的清空/冲突检查，回执缺失不能作为忽略残留规则的依据。

## 预览、中断与输出

`--check` 只读检查 SSH 目标基本前提，不传送载荷。`--preview` 会在目标创建私有协调目录及锁、传输并暂存载荷、生成临时私有输入，以及执行安装/升级预检；首次安装还会在临时目录验证管理员凭据生成。它会写入暂存文件，不停止服务、不安装配置或 unit，也不安装管理员凭据。正常命令才执行安装／更新。

载荷先复制到同一 incoming 父目录内的独立暂存目录，完整校验后才发布为对应 manifest 摘要的目录；普通复制失败会清理本次暂存，重试不会复用半成品。已存在的正式缓存在执行其中的入口前重新检查精确文件集与每个字节摘要，漂移、缺失或额外文件均拒绝。进程终止留下的临时目录和早期版本遗留的不完整正式缓存需按归属审阅，工具不会删除未知目录来重试。

失败不会自动重复系统变更。目标 `/etc/cocoproxy-install/remote-last.json` 记录阶段、摘要、先前服务/runtime 意图及已取得的维护恢复令牌，保持 root:0600；这是本次操作的状态记录。出现失败或未完成记录时停止普通部署，先按[安装与维护](deployment.md)审阅实际状态。安装器收据与锁仍是文件安装的权威证据，不能删除它们重试。远程协调失败涉及 runtime、路由器与服务恢复时，应先核对这些独立状态；维护令牌只接受未被后续操作改变的暂停标记，不能强行重放，也不能只依据 SSH 返回值判断成功。

默认只输出固定阶段、提交、摘要和验证结果，不输出配置、口令、原始系统错误或订阅。仅清单中的发行文件进入传输，明确拒绝 `.local/`、`.git/` 和目录链接。运行依赖由发行清单明确列入，不能把开发工作区的 node_modules 整体打包。SSH 临时上传和临时管理员输入在收尾清理；旧正式 release 按安装器规则保留，不称为业务备份。首次提供的私有输入是否继续保留由操作者管理。
